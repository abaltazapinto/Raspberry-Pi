# Incident Report — Tailscale + Pi-hole DNS failure

**Date:** 2026-09-18  
**System:** Raspberry Pi 5 + Pi-hole + Tailscale  
**Client used for diagnosis:** Debian `baltazar`  
**Goal:** Use the Raspberry Pi/Pi-hole remotely through Tailscale and understand why Internet-by-IP worked while DNS resolution failed.

---

## 1. Final topology

```text
Debian baltazar
Tailscale IP: 100.92.44.113
        |
        |  Tailscale overlay network
        v
Raspberry Pi
Tailscale IP: 100.116.30.48
LAN IP:       192.168.1.21
        |
        +--> Pi-hole / pihole-FTL :53
        |
        +--> upstream DNS
             final configured:
             1.1.1.1
             1.0.0.1
```

Other Tailscale device observed:

```text
Samsung A56: 100.114.244.36
```

---

## 2. Initial symptom

The Debian machine had Internet connectivity by IP:

```bash
ping 1.1.1.1
```

worked, but names such as `github.com` did not resolve.

Example:

```bash
getent hosts github.com
```

returned nothing.

This is a classic distinction:

```text
IP connectivity works
DNS resolution fails
```

So the first hypothesis should be **DNS**, not routing.

---

## 3. Debian DNS was controlled by Tailscale

Initial `/etc/resolv.conf`:

```text
# resolv.conf(5) file generated by tailscale
nameserver 100.100.100.100
nameserver fd7a:115c:a1e0::53
search tail383b3a.ts.net
```

`100.100.100.100` is the Tailscale DNS resolver address.

The resolver itself was reachable by ICMP:

```bash
ping -c 3 100.100.100.100
```

but DNS queries timed out:

```bash
dig @100.100.100.100 github.com
```

Result:

```text
communications error to 100.100.100.100#53: timed out
no servers could be reached
```

Important lesson:

```text
ping DNS_IP
```

only proves reachability to the IP.

It does **not** prove that the DNS service on UDP/TCP port 53 is working.

---

## 4. Temporary recovery on Debian

Tailscale DNS acceptance was disabled on the Debian machine:

```bash
sudo tailscale set --accept-dns=false
```

After that, `/etc/resolv.conf` returned to NetworkManager control:

```text
# Generated by NetworkManager
search home
nameserver 192.168.1.1
nameserver 2a01:11:1020:47b0::1
```

Result:

```text
github.com resolved again
browser access worked again
```

### Current implication

With:

```bash
sudo tailscale set --accept-dns=false
```

the Debian machine still uses the **Tailscale network**, but it does not automatically use Tailscale DNS/MagicDNS.

Tailscale IP access still works, for example:

```bash
ssh <user>@100.116.30.48
```

---

## 5. Testing Pi-hole over Tailscale

A direct query from Debian to the Raspberry Pi was attempted:

```bash
dig @100.116.30.48 github.com
```

Initially this timed out.

SSH to the same Raspberry Pi over Tailscale worked, which proved:

```text
Tailscale network path: working
SSH: working
DNS through Pi-hole: failing
```

---

## 6. Verify who owns port 53

On the Raspberry Pi:

```bash
sudo ss -lntup 'sport = :53'
```

Output:

```text
udp   UNCONN 0 0 0.0.0.0:53  0.0.0.0:* users:(("pihole-FTL",pid=1724,...))
udp   UNCONN 0 0 *:53         *:*       users:(("pihole-FTL",pid=1724,...))
tcp   LISTEN 0 32 0.0.0.0:53 0.0.0.0:* users:(("pihole-FTL",pid=1724,...))
tcp   LISTEN 0 32 [::]:53    [::]:*    users:(("pihole-FTL",pid=1724,...))
```

This proved:

```text
pihole-FTL is running
port 53 is open at socket level
FTL listens on IPv4 and IPv6
```

### Important troubleshooting mistake encountered

A previous `ss` output showing:

```text
10.42.0.1:53 -> dnsmasq
```

came from the **Debian machine**, not the Raspberry Pi.

Always check the shell prompt before interpreting network diagnostics:

```text
abaltaza@baltazar:~$      -> Debian
abaltaza@raspberrypi:~$   -> Raspberry Pi
```

---

## 7. Pi-hole listening mode

Pi-hole listening mode was checked with:

```bash
sudo pihole-FTL --config dns.listeningMode
```

It was set to:

```text
ALL
```

The explicit command to configure it is:

```bash
sudo pihole-FTL --config dns.listeningMode "ALL"
```

`ALL` allows queries received on all interfaces.

### Security note

Do not expose UDP/TCP port 53 from the Raspberry Pi directly to the public Internet.

Using port 53 inside LAN/Tailscale is different from port-forwarding DNS from the WAN.

---

## 8. Prove that Tailscale DNS packets reach the Raspberry Pi

On the Raspberry Pi:

```bash
sudo tcpdump -ni tailscale0 port 53
```

Observed traffic included:

```text
100.92.44.113.xxxxx > 100.116.30.48.53: A? github.com.
100.114.244.36.xxxxx > 100.116.30.48.53: A? ...
```

This proved:

```text
Debian/Samsung DNS packets
        |
        v
Tailscale
        |
        v
Raspberry tailscale0
```

were reaching the Raspberry Pi.

Therefore the basic Tailscale transport path was not the blocker.

---

## 9. Local Pi-hole test

External query through the local Pi-hole initially failed:

```bash
dig @127.0.0.1 github.com
```

But a Pi-hole-local name worked:

```bash
dig @127.0.0.1 pi.hole
```

Result:

```text
pi.hole. 0 IN A 127.0.0.1
SERVER: 127.0.0.1#53
Query time: 0 msec
```

This was a very important discriminator.

It proved:

```text
pihole-FTL process         OK
local DNS processing      OK
port 53                    OK
local synthetic Pi-hole DNS OK
external recursion/forwarding was the failing part
```

---

## 10. Check Pi-hole upstream DNS

Configured upstreams:

```bash
sudo pihole-FTL --config dns.upstreams
```

Initial result:

```text
[ 9.9.9.9, 149.112.112.112 ]
```

These are Quad9 resolvers.

A direct test was attempted:

```bash
dig @9.9.9.9 github.com
```

and timed out during the incident.

A direct UDP query to Cloudflare also timed out at one point:

```bash
dig @1.1.1.1 github.com
```

However TCP DNS worked:

```bash
dig +tcp @1.1.1.1 github.com
```

and later UDP DNS to Cloudflare also worked:

```bash
dig @1.1.1.1 github.com
```

Example successful answer:

```text
github.com. IN A 140.82.121.3
SERVER: 1.1.1.1#53
Query time: 15 msec
```

### Engineering conclusion

Do **not** record "Quad9 was definitely broken" as proven fact.

What is proven is:

1. Pi-hole was configured with Quad9 when external forwarding failed.
2. Direct DNS tests showed transient failures during diagnosis.
3. Cloudflare later worked directly.
4. After Pi-hole upstreams were changed to Cloudflare, Pi-hole external resolution worked.

So the strongest defensible conclusion is:

> External upstream resolution was the failing part of the chain. Changing the Pi-hole upstream configuration from Quad9 to Cloudflare restored working external DNS. The evidence does not fully prove whether the original root cause was Quad9 itself, a transient UDP/network condition, or Pi-hole upstream state/configuration.

This distinction matters in future incident reports.

## 11. Route used by Raspberry Pi

Command:

```bash
ip route get 1.1.1.1
```

Output:

```text
1.1.1.1 via 192.168.1.1 dev wlan0 src 192.168.1.21 uid 1000
```

Interpretation:

```text
destination : 1.1.1.1
gateway     : 192.168.1.1
interface   : wlan0
source IP   : 192.168.1.21
```

Do not confuse:

```text
src 192.168.1.21
```

with the gateway.

The gateway is the address after:

```text
via
```

## 12. Change upstream DNS to Cloudflare

Pi-hole upstreams were changed to:

```bash
sudo pihole-FTL --config dns.upstreams '[ "1.1.1.1", "1.0.0.1" ]'
```

Verification:

```bash
sudo pihole-FTL --config dns.upstreams
```

Result:

```text
[ 1.1.1.1, 1.0.0.1 ]
```

## 14. Final remote test through Tailscale

From Debian:

```bash
dig @100.116.30.48 github.com
```

Successful result:

```text
status: NOERROR
github.com. IN A 140.82.121.3
SERVER: 100.116.30.48#53
Query time: 24 msec
```

This proves remote DNS over Tailscale works:

```text
Debian 100.92.44.113
        |
        | Tailscale
        v
Raspberry 100.116.30.48:53
        |
        v
Pi-hole
        |
        v
Cloudflare upstream
```

The response also contained:

```text
EDE: 3 (Stale Answer)
TTL: 0
```

This did **not** mean the query failed. The DNS response was successful (`NOERROR`) and contained an A record. If stale answers persist, investigate Pi-hole caching separately.

Interpretation:

```text

```


# Troubleshooting model to remember

Do not randomly change configuration.

Walk the chain:

```text
1. Does IP connectivity work?
        |
        v
2. Does hostname resolution work?
        |
        v
3. Which DNS server is configured?
        |
        v
4. Is that DNS IP reachable?
        |
        v
5. Does port 53 actually answer?
        |
        v
6. Is the DNS daemon listening?
        |
        v
7. Do packets arrive at the server?
        |
        v
8. Can the DNS server resolve local names?
        |
        v
9. Can it reach its upstream resolver?
        |
        v
10. Test the complete client -> DNS -> upstream chain
```

This incident showed why each layer matters.

# Key lesson

The useful mental model from this incident is:

```text
"Internet works" and "DNS works" are different questions.
```

And:

```text
"ping to a DNS server works" does not mean "DNS service works".
```

Use:

```bash
ping <IP>
```

for IP reachability, and:

```bash
dig @<DNS-IP> <hostname>
```

for the DNS service itself.

Finally, always identify **which machine the command is running on** before interpreting `ss`, `ip route`, `tcpdump`, or DNS output.
